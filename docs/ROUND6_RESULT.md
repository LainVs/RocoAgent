# 本轮结果：BAND 两级词表 —— 覆盖率补足（2026-11-23 08:2x）

**「扬沙」这个合法技能被系统性拒绝**。

OCR 一直读得对，被拒的只有**词表**。

## 根因：species_skills 数据不全

```
species WHERE name='卡瓦重'  ->  id 3042 / 3294 / 3295 / 3296（同名 4 行）
species_skills 跨这 4 行取并集 = 58 个
  -> 含「筛管奔流」= True
  -> 含「扬沙」     = False   <- 但游戏里确实带着
```

「扬沙」有 147 只属主，其中包含 `卡瓦重（雪山附近的样子）`（另一个变体
species 行），但**基础名 卡瓦重 名下没挂这条**。

## 修法：两级词表

| 层级 | 来源 | 规模 | 门槛 | 权威性 |
|---|---|---|---|---|
| 1 | `my_team.moves`（用户亲手配） | 4 | 0.80 | 最高 |
| 2 | `species_skills` 可学池 | 40~60 | 0.80 | 中（已知不全） |
| 3 | 全库 | 1045 | 0.90 | 兜底 |

**为什么不放宽门槛**：降到 0.30 会立刻引入误配 ——「扬沙」在全库
1045 个技能里有大量近邻。覆盖率不能拿安全性来换。

## 实测效果

同一帧、同一次 OCR：

| 词表 | 大小 | `扬沙` 匹配 | 结果 |
|---|---|---|---|
| 配置（新第一级） | 4 | **1.00** | **采纳** |
| 可学池（旧） | 58 | None 0.00 | 被拒 |

**不引入误配**：`火焰切割` / `岩脉崩毁` / `吞噬` 在卡瓦重的配置词表下
仍然 0.00 被拒。

## 数据卫生（审计脚本修正判据）

原判据「不在 species_skills 池外 = 脏数据」**过严**，会把「扬沙」误报。
修正为三选一，任一成立即可信：

1. 在 `species_skills` 可学池内
2. 在**该精灵 `my_team` 配置**的 4 个技能内（权威性最高）
3. 该技能属主 >= 50（通用技能，大量精灵都能带）

判脏的充分条件：三条**全部**不成立。

修正后体检结果：**20 条记录，0 条不可信**。

`先发制人` 同时出现在冰钻布鲁斯/恶魔狼/武者鸡名下看着可疑，但它有
**193 个属主**，是通用技能，正常。

审计脚本已固化为 `scripts/audit_session_moves.py`。

## 诊断增强

`SM.raw_of()` 现在返回 4 项，第 4 项是 `tier`。日志变成：

```
BAND -> 卡瓦重 槽2 未识别 (conf 0.00 < 0.80) raw='扬沙' vocab=4(config)
```

这两种被拒需要完全不同的处置，必须在日志里一眼分开：

- `tier=config` 被拒 -> 配置里真没这个词，**用户换队了**
- `tier=species` 被拒 -> 可能只是可学池数据不全，**技能本身是对的**

## 测试

新增 `test_band_vocab.py`（13 条断言），其中两条特别值得留意：

- `species_skills 不含「扬沙」` —— 把"数据不全"这个事实**锁进测试**。
  将来数据补齐了这条会 FAIL，提醒重新评估第一级是否还必要。
- `配置词表下 1.00 / 可学池下 0.00` —— 对照证明修复有效，而不是靠
  宽松阈值蒙过去。

`test_session_moves` 的 live-frame 用例改用虚构精灵名：真实精灵名会被
第一级配置词表拦截（fixture 里印的「力量增效」不在音速犬配置里），
那是新逻辑的预期行为，换虚构名才能覆盖到 ROI 本身。

8 个测试文件全 PASS。
