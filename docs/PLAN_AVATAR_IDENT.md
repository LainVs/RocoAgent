# 用 `pet_avatars` 当识别通道（已实现）

> 日期：2026-11-22
> 代码：`src/avatar_ident.py`（通道）、`scripts/bench_avatar_ident.py`（评测）
> 测试：`src/test_avatar_ident.py`
> 数据：`assets/pet_avatars/<图鉴id>.png`（639 张，来源 洛克PVP助手）
> 真值：`assets/portraits_foe/*.png`（162 张已标注实机 HUD 裁图）

---

## 一、结论

1. **`pet_avatars` 和实机 PvP HUD 头像就是同一张插画**，HUD 只是做了约 1:1
   的居中裁切。证据见 `docs/img/avatar_align.png`。
2. 它已经作为**第三条身份通道**接入：
   - `foe_ident` 第 3.5 步（独立计算器/伤害计数器走这条）；
   - `robot._check_foe` 的第三通道（机器人走这条）；
   - `standalone` 的我方兜底（必须命中 `my_team`）。
3. 在同一批 162 张真值上，它和 ONNX **互补性很强**：
   单独 74.2%（普通配色），两者并集 **88.7%**（普通配色）。
4. 高置信档（`score>=0.60 且 margin>=0.03`）实测 **95~96% 精确**，
   所以允许它单独定名；低置信一律不投票，交给 ONNX / 特性面板。
5. 异色/炫彩会掉点（56.9%），但用置信度阈值后表现为"不确定"而不是"认错"。

---

## 二、几何关系（踩过的坑）

`pet_avatars` 是 128×128 带 alpha 的方图；HUD 框是 84×76（对面）/
76×80（我方）。最初直接做多尺度 NCC，正确头像的分数反而低于错误头像。

| 坑 | 表现 | 处理 |
|---|---|---|
| 透明像素 RGB 未定义 | 大片黑/白参与相关，压过主体 | 按 alpha 合成到假想背景 |
| HUD 背景/属性图标占约 40% | 背景差异主导分数 | 中心椭圆 mask |
| 缩放关系搞反 | 以为 HUD 是放大图 | 实测 **≈1:1**，窗口更"高" |
| 裁切中心不对 | 头部在模板里偏小/偏低 | 中心取 `(0.5w, 0.42h)`，`z_h` 1.0~1.6 |
| 通道顺序 | `grab_client` 是 RGB，PNG 是 BGR | 查询时 RGB→BGR |
| 抓框带 margin | 104×96 喂进去头部占比变小 | 头像通道统一用**紧框**（margin=0） |

最后一条尤其容易踩：同一张 `寂灭骨龙` 裁图，紧框 84×76 得分 **0.864**，
补 10px 边后只有 **0.435**——通道直接失效。所以 `identify_screen()` 默认
`margin=0`，和 `portrait_onnx.hud_crop()` 的 margin=10 是两套约定，不要混。

## 四、结果

```
subset                  n   pool    avatar      high      onnx    union
all                   162   39.3     67.3%     46.9%     57.4%    81.5%
plain                  97   38.8     74.2%     59.8%     64.9%    88.7%
#variant               65   40.1     56.9%     27.7%     46.2%    70.8%
identifiable          141   41.1     76.6%     53.2%     58.2%    85.8%
identifiable/plain     87   41.0     81.6%     65.5%     64.4%    90.8%
```

- `high` 列 = 只有高置信票才计入的 Top-1 覆盖率。
- `union` = 任一通道 Top-1 对就算对，是"理想仲裁器"的上限，不是已实现的融合。
- 高置信票共 **80 次，95.0% 正确**（标定脚本 96.2%，差异来自候选池边界）。

**覆盖率**（去掉括号/首领前缀后统计）：

```
DB 789 个名字 | 头像 507 | ONNX 619 | 并集 707 (90%)
头像独有 88 个 | ONNX 独有 200 个 | 重合 419 个
```

不加属性约束时两者都只有 **47~49%**，所以属性硬约束仍是命门。

## 五、置信度标定（线上阈值来源）

在 141 张可识别真值（属性约束后）上统计：

```
正确  n=108  score 均值 0.670  p10 0.366 | margin 均值 0.211 p10 0.028
错误  n=33   score 均值 0.499  p10 0.307 | margin 均值 0.045 p10 0.008
```

| 策略 | 保留 | 精确率 | 覆盖率 |
|---|---|---|---|
| score ≥ 0.50 | 109 | 81.7% | 77.3% |
| score ≥ 0.55 | 97 | 87.6% | 68.8% |
| score ≥ 0.60 | 84 | 92.9% | 59.6% |
| **≥0.60 且 margin ≥0.03** | 78 | **96.2%** | 55.3% |
| ≥0.55 且 margin ≥0.03 | 87 | 93.1% | 61.7% |

线上分三档（`avatar_ident.HIGH_SCORE / HIGH_MARGIN / LOW_SCORE`）：

```
>=0.60 且 margin>=0.03   -> high：允许单独定名
0.50 ~ 0.60              -> low ：只参与排序
<0.50                    -> none：不投票
```

## 六、性能

实测本机：

```
冷启动构建银行：2.8 s（639 id × 12 视角 = 7668 个 3072 维向量）
缓存加载：      0.19 s（data/cache/avatar_bank_<side>.npz）
单次打分：      ~21 ms（9 次 ±2px 平移的矩阵乘）
内存：          89 MB / side
```

- 银行按 `assets/pet_avatars` 的文件数 + 最大 mtime 失效；
  目录指纹本身缓存 30 秒，避免 10Hz 轮询时每帧 stat 639 个文件。
- `AT` 以 **(dim, views)** 连续数组存储：早期存成 `A` 再 `.T`，每次矩阵乘
  都要复制 94 MB，单次查询 175 ms；改完降到 21 ms。
- 我方和对面是两套几何（84×76 vs 76×80），银行按 side 分开、**惰性加载**。

## 七、接入位置（已实现）

### 7.1 `foe_ident.identify()` —— 第 3.5 步

```python
# 属性 -> 候选池 -> 名字/昵称 -> [avatar 通道] -> 头像模板 -> ONNX
av = avatar_ident.identify_screen(screen, side=side, candidates=cands)
if av and av[0]["conf"] == "high" and _accept(av[0]["name"]):
    out.update(name=av[0]["name"], source="avatar", conf=av[0]["score"])
    return out
```

仍然必须过 `_accept()` 的属性否决。候选池里一个都没有时返回空，
不会退化成全库乱猜。

### 7.2 `robot._check_foe()` —— 第三通道

机器人这条链路不经过 `foe_ident`，所以单独接：

- 输入是 104×96 的带 margin 裁图，调用时传 `margin=portraits.SEARCH_MARGIN`；
- 只在两种情况下覆盖已有名字：
  - 现在还没有名字；
  - 当前名字来自模板通道且置信度 < 0.90（模板 0.60 只有约 76% 正确）。
- ONNX 高置信（≥0.90）不覆盖，保持原有锁逻辑；
- 采纳后写 `foe_ident_source="avatar"`，模板兜底块看到这个标记就不再
  用 0.60~0.95 的模板反过来覆盖它。

### 7.3 `standalone` —— 我方兜底

在「名字 / 血条绝对值」之后、「头像模板」之前，要求命中 `my_team`。
`assets/portraits`（self）目前只有 20 张标注模板 + 1001 张 `_unknown_*`，
头像通道正好补这个缺口。

### 7.4 缓存与预热

`data/cache/` 是派生数据，已加入 `.gitignore`。删掉后下次自动重建。

银行冷构建 2.8 s，**不能让它发生在对局/HTTP 请求里**：

- `robot.run()` 在连板子之后、进主循环之前 `avatar_ident.bank("foe")`；
- `standalone.warmup()` 在后台线程里先建银行，再跑第一次 identify。

## 八、已知限制（诚实清单）

1. **只有普通配色**：639 张都是一套配色。变体子集 56.9%，比普通低 17 个点；
   炫彩可能更低。→ 靠高置信阈值 + 特性面板兜底，不硬猜。
2. **特殊 id 没有头像**：`990000112`、`2000000191` 这类形态/首领 id 不在
   图鉴头像里（162 张真值里有 21 张属于这类）。→ 保留 ONNX / 特性反查。
3. **属性约束是上限**：本文 67~91% 都建立在"属性读对"上。线上第二个属性
   经常被挡，池子会变大、精度会降。
4. **样本偏差**：162 张里 65 张是变体，部分真值可能有标注误差。
   ONNX 文档里的 85.6% 是在另一批 165 帧上测的，不可跨来源比较。
5. **不同分辨率**：真值都是 84×76（基准 2560×1600）。4:3 下 HUD 贴边锚定，
   裁框走 `portraits.foe_box_for` 的换算；头像通道对缩放不敏感（内部统一
   重采样到 32×32），但仍需按基准坐标裁。

## 十、下一步（按性价比）

1. **跑一晚看线上命中率**：日志里会出现 `FOE -> xxx (0.xx, avatar)`。
   重点看两件事：高置信票有没有认错、`#variant` 有没有被误判成 high。
2. **合成 HUD 训练集**：既然确认了"HUD = 头像的 1:1 裁切"，就可以从头像
   渲染出几十万张 HUD 风格样本（裁切 + 蓝色蒙层 + 场景背景 + JPEG 噪声），
   训练一个覆盖 995 个名字的分类器。这是把 90% 覆盖率推到 100% 的正路。
3. **变体样本继续攒**：低置信 + 特性面板确认后，把 HUD 裁图按 `#异色`
   存进 `assets/portraits_foe`，模板库自然长大。
4. **PCA 压缩银行**：3072 → 128 维可把 90 MB 压到 4 MB，精度预计掉 1~3 点，
   等银行成为部署负担时再做。
