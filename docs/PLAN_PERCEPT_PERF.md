# 计划：感知耗时（控制台一直标红的 387ms）

> 2026-11-21 · 基于真机实测（2560×1600 客户端，venv 解释器）
> 代码：`src/winio.py`（`grab_frame` / `crop_frame`）、`src/perceive.py`（`observe` / `_skill_meta`）
> 基准：`src/bench_perceive.py`、等价性测试 `src/test_perceive.py`

---

## 0. 结论先说

控制台上的 `fps_ms` 387ms **不是技能栏图像处理慢**（那部分只有 32ms），
而是**每帧做了 5 次独立抓屏**（~104ms）+ **每帧查两次数据库**（51ms）。

| 项 | 改前 | 改后 |
|---|---|---|
| 抓屏 | 5 次 × ~20.7ms = **~104ms** | 1 次整窗 = **62.8ms** |
| 技能表查询 | 2 次 sqlite = **51ms** | 缓存命中 = **0.006ms** |
| 技能栏图像处理 | 32ms | 32ms（未动） |
| 战斗态 observe 合计 | **约 190ms** | **约 100ms** |

大厅态本来就没那么慢（实测 p50 70~95ms），387ms 是战斗态的峰值：
`bar=True` 才会走技能栏 + 倒计时 + 能量 + 技能表查询那几段。

> **计时口径**：抓屏和数据库这两项是**确定性**测量（同一操作重复取中位）。
> 端到端 `observe()` 的墙钟时间在开发机上波动很大（同一份代码连跑三次
> 能差 ±20ms），所以不拿它当结论。改动的方向性收益由「抓屏次数 5→1」
> 和「数据库查询 每帧→每 30 秒」两条决定，与机器负载无关。

## 1. 怎么定位的

### 1.1 先证伪"技能栏画不出来"

日志里满屏 `state battle=True bar=False`，看起来像"技能栏读不到"。
但 15 秒一次的状态日志**不区分回合**——技能卡只在轮到我方时才画出来，
采样落在对面回合就是 `bar=False`，这是正常现象。

`logs/turns.jsonl` 里 3161 个回合、12644 个技能槽：

```
空槽    236  (1.9%)     胶囊没找到
含 ?    340  (2.7%)     数字读了一半
完整   12068 (95.4%)
```

**技能栏本身是好的**。所以 `bar=False` 是采样假象，`387ms` 才是真问题。

### 1.2 再拆耗时

`robot.py:577` 的 `last_obs_ms` = `observe()` + 技能稳定化。用 cProfile
打在真实屏幕上：

```
15 次 grab_s  →  0.243 s   （5 次观察 = 每次 49ms 抓屏）
 5 次 find_pills → 0.090 s  （每次 18ms）
```

`mss` 的每次 `grab` 有 **~20ms 固定开销**，和区域大小几乎无关：

| 区域 | 尺寸 | 耗时 |
|---|---|---|
| MY_BAR | 244×20 | 17.1 ms |
| FOE_BAR | 245×20 | 16.5 ms |
| SKILL_BOX | 530×1040 | 17.3 ms |
| CNT_ROI | 340×150 | 17.8 ms |
| 整窗 | 2586×1671 | 62.8 ms |

抓 244×20 和抓 530×1040 一样慢 —— 所以**减少次数**才是关键。
实测 4 个区域逐个抓 = 82.9ms，一次整窗 = 62.8ms。

### 1.2.1 一个差点漏掉的坐标陷阱

第一版改成了抓**客户区**（2560×1600）。合成帧测试立刻报错：

```
CNT_ROI = (1120, 55, 340, 150)
sbox(): (y - BASE_OFF_Y) * sy = (55 - 58) * 1 = -3
```

倒计时那块 ROI 的 y **比边框偏移还小 3px**，换算到客户区就是负坐标。
`grab_s` 直接对着屏幕抓，负坐标落到标题栏里照样能返回像素；
只抓客户区就整个丢掉了 —— 表现为 `countdown` 永远 False。

所以现在抓的是**整窗**（2586×1671，含 13px 边框 + 58px 标题栏），
和 `grab_s` 的窗口坐标口径完全一致。代价是帧大 5%，`crop_frame`
多做一次 `+ client_off` 的平移。

### 1.3 数据库是第二个大头

`_fix_status_kinds` 和 `attach_skill_names` **每帧各开一次 sqlite 连接**：

```
_fix_status_kinds   中位 27.1 ms
attach_skill_names  中位 24.4 ms
```

但这两件事查的东西**只跟 `my_name` 有关**：我方 4 个槽位装哪 4 个技能，
一局里只有换精灵时才变。每帧重查是纯浪费。

实测：未命中 40ms → 命中 **0.006ms**。

## 2. 改了什么

### 2.1 `winio.Screen.grab_frame()` / `crop_frame()`

```
grab_frame()  -> 整块客户区 BGRA 原样 + 缩放比
crop_frame()  -> 从整帧切一块，转 RGB，缩回基准尺寸
```

**整帧不转 RGB**：4MP 的 `cvtColor` 要 ~20ms，而切片是小图，
每块转一次总共不到 1ms。

### 2.2 `Perc.observe()` 只抓一次

5 个区域全部从同一帧切片。这一帧是**同一瞬间**的画面，
顺带消掉了一个隐患：以前 5 次抓屏之间有几十毫秒间隔，
血条和技能栏可能来自不同时刻。

### 2.3 技能表按 `my_name` 缓存

```
_team_snapshot()   team_db.dump_team()，15s
_skill_meta(name)  moves / powers / names / dash_costs，30s
```

「查数据库」和「按帧判断」拆开：前者缓存，后者保持纯计算。
路线 2（队伍没配 moves，用变化技能耗能推断）里 `v <= 60` 这类判断是
**帧相关**的，仍然每帧算，只是不再重连数据库。

换队/改队伍配置最多 30s 内生效，对实战足够。

## 3. 怎么验证没改坏

这类"提速重构"最怕**悄悄改变语义**：血条偏 2px、槽位少一个，
日志上只是数字变了一点，不会报错，但直接影响出招。

`src/test_perceive.py` 的做法：把改动前的 `perceive.py` 从 git
（tag `ui-m38`）取出来当独立模块，用**同一帧画面**跑新旧两版，
逐字段比对（`battle/my_ui/foe_ui/my_pct/bar/npills/countdown/energy/myturn`
以及每个槽位的 `text/value/kind/color/score/plate/lit/skill_name/skill_kind`）。

> **必须是同一帧**。第一版是"对着屏幕各跑一次"，结果 `npills` 老 6 新 7——
> 不是重构改坏了，是两次抓屏之间游戏画面在动。现在先 `capture_live()`
> 抓一帧冻住，两版都跑这一帧，结果才可复现。

覆盖四条技能表分支：

| 用例 | 走哪条路 | 期望 |
|---|---|---|
| `音速犬` | team_db 有 moves，槽位 1 power=0 | 强制成 dash |
| `银月狼王` | team_db 有 moves，四张都有伤害 | 不改 |
| `虚无缥缈` | team_db 没有 | 走耗能推断，不报错 |
| `None` | 还没认出我方是谁 | 完全 no-op |

外加四条：
- **合成帧**：2586×1671 整窗黑底 + 真实血条 + 真实技能栏（171/114/45/102），
  让 `bar=True`/`battle=True` 分支真的跑到
- **回退路径**：注入只有 `grab_s` 的 Screen（`providers.py` 允许传
  `screen=`），必须自动退回逐区域抓，输出一致
- **7 兜底**：`42?`→`427`、`1?1`→`171` 必须补回来，且 `recovered` 之外
  的字段与旧版完全一致
- **110 帧旧语料**：`logs/digits/frames` 上的读数必须仍是 0 个 `?`，
  且 7 判据在 864 个字形上「查全 108/108、误判 0/756」

全部一致。

## 4.1 顺便修掉了数字 7 的系统性误判

同一批 `bar_partial_*.png` 顺带暴露了一个**准确率**问题（不是性能）。

173 张失败帧、635 个技能槽里，被拒识别的字形 152 个。按形状聚类：

```
簇 0   n=115   全是同一个字形 —— 细斜杠的 7
簇 1~14  n=37  卡面图案噪点（云状 / 斜条 / 三角 / 白块），根本不是数字
```

也就是说 **76% 的读数失败是「7」这一个数字造成的**。

### 根因

模板集是用 `logs/digits/frames` 那 110 张帧建的。那批语料里 `7` 只出现过
一次（`70`），而且是**粗竖直**的写法。实盘还有另一种**细斜杠**的 7：

| 来源 | 字形 | 和模板最高相关度 |
|---|---|---|
| `70`（训练语料） | 粗竖直 | 1.00（就是它自己） |
| `427` / `171`（实盘） | 细斜杠 | **0.45** |

`TPL_MATCH = 0.55`，所以细斜杠的 7 一律被判成 `?`，而最像的模板恰好是 `2`
（0.45），差一点就可能读成 2。

试过 blur、梯度、距离变换、骨架化、放宽掩码阈值 —— 全部 `21/23`
（两个 7 一直错）。因为这不是笔画粗细问题，是**同一个数字的两种写法**。

### 修法：结构判据兜底

模板匹配对"两种写法"无能为力，但两种写法的**结构**一样。实测三段墨迹的
水平跨度（占字形宽度比例）：

| 数字 | top(0~22%) | bottom(78~100%) | middle(40~60%) |
|---|---|---|---|
| **7** | 0.71~1.00 | **0.36~0.43** | **0.29~0.43** |
| 2 | 0.86 | 0.86~0.93 | 0.43~0.50 |
| 4 | 0.64~0.71 | 0.29~0.71 | **0.79** |
| 5 | 0.86 | 0.93 | 0.86 |
| 1 | 0.57 | **1.00** | 0.29 |

只有 7 同时满足「顶部满宽 + 底部窄 + 中部窄」：4 的中间是宽的，
1/2/5 的底部是宽的，0/3/6/8/9 底部也宽。

代码在 `perceive.read_skill_with_fallback()`：**只在模板已经返回 `?`
时才启用**，绝不覆盖高置信度的模板结果；补上的槽位带 `recovered=True`。

### 实测

```
173 张失败帧的 '?'：210 -> 64（消除 70%）
  其中 7 兜底消除 120 个
  位数闸门把 "??????" / "??????7?" 这类长乱码并成单个 '?'
触发兜底的槽位：119

人工核对 4 例（放大截图逐字看）：
   ?5  -> 75    38? -> 387    2?0 -> 270    51? -> 517     全部正确

110 帧旧语料（864 个字形）上的判据表现：
   真实 7   108/108 全部认出
   非 7     0/756 误判
   整体 '?'  0 个（改前也是 0，无回归）
```

剩下的 64 个 `?` 里绝大多数是 `??` / `????` 这类**卡面图案被当成字**的噪声，
只有 1 个是真正的数字槽（`3?`）。批次不同，具体数目会有浮动。

### 另一半：4 位以上的读数是切分错误

同一批语料还暴露出更危险的一类：`1062` / `1294` / `??????`。
它们全部 >999，真实值都是 3 位数（106 / 129）—— 多切进了一个字形。

`turns.jsonl` 里 3161 个回合有 **25 个（0.8%）** 中招。后果是
`policy_v2` 会把 1062 当成"必定秒杀"（`w_ko` 权重 0.30），
而 `??????` 会被 `_est_value` 按位数估成 **10^5 = 100000**。

卡面伤害本作最多 3 位（实测最大 ~700，精灵血量都在 500 上下），
所以 `read_skill_with_fallback` 和 `_est_value` 都加了一道位数闸门：
超过 3 位 -> 当作"读不出"（`text="?"`、`value=None`、`rejected=原位数`）。

## 5. 没做的事

- **卡面图案被误当数字**（`??`）。位数闸门已经挡住了 4 位以上的，
  剩下 `??` 这类 2 位的会被 `_est_value` 估成 10。影响很小（10 伤害
  在任何比较里都是最末位），所以没继续动。要彻底解决得先判断
  "这个胶囊里到底有没有数字"，属于切分逻辑，单独做。
- **`fps_ms` 仍然只报"最近一帧"**。一次 GC 或 DWM 抖动就能让它短暂
  变红。健康面板已经改成按轮询间隔判（见 `docs/FRONTEND.md` §三），
  要更进一步得做滚动 p95，属于契约改动，单独做。
- **抓屏仍有 63ms**（占 observe 的 ~75%）。mss 每次 grab 有 ~20ms
  固定开销，要突破得上 DXGI Desktop Duplication（约 10ms），
  需要新依赖 + 几百行 ctypes。当前 5Hz 对回合制游戏够用，没做。
