## 数据

从 turns.jsonl 的 210 场对局里，**104 场动作数 ≤2**。按 bot_stdout.log
的 MATCH END 签名分类（66 条 END 记录）：

| 类型 | 数量 | 特征 |
|---|---|---|
| D 健康（≥5 动作） | 26 | 正常对局 |
| A 幻影（0 秒） | 16 | END 时长 0s——对局从未真正开始（多半是重启后在大厅误判 START） |
| B 打了但没出手（n≤1） | 14 | 有时长但整局只按了 0~1 次 |
| C 短局（2~4 动作） | 10 | 真打了但提前结束 |

## B 类根因链（逐案核对 08:40 那局）

```
08:40:17 MATCH START（进场时我方 0 血——上一局残留的濒死状态）
08:40:58 FAINT -> 强制换人面板（panel scan 的 click 1090,754）
08:41:06 FAINT -> recovered（血量回 100%）
08:41:25 FOE -> 画间沉铁兽 (0.78)   ← 对面换人了
08:41:36 state battle=False          ← 对局实际已结束（对面投了/超时）
```

review 文件证实：这场从 08:40:20 到 08:40:44 只有 2 个回合记录，
双方血量 100→64 / 100→66 —— **是真实对局，但只打了两个回合就结束了**。
不是机器人卡死，是对局本身短（对面秒投或运气局）。

## 'GATE read not stable' 的分布

全日志 1444 次，其中 08:00~09:00 一小时 118 次（该小时总行数 4.6%）。
与 08 点的 3 场低动作局时间重合——**技能栏读数抖动确实在吃决策窗口**，
但 STABILIZER + 3 秒 bypass 已把它兜住（多数 3 秒后成功出招）。

## 结论

1. **104 场低动作 ≠ 104 场故障**：16 场是幻影计数（重启残留），
   14 场是真实短局（对面快投），实际"卡死"比例比表面低得多。
2. **真正的损失源**：A 类幻影局污染了胜率分母 —— 夜报的"210 场"
   应该剔除幻影局再算动作率。
3. 值得做的小修：MATCH START 在 battle=False 的帧里不算数
   （要求 live 证据已存在，但 0 血进场那帧的 battle=True 是上一局
   残留 → 应该把 START 的判据再加一条：me_pct>0 或非换人面板）。

## 附：robot.lock 里的旧 PID（2026-11-22 深夜）

selfcheck 报 robot.lock 空闲、但文件里写着 PID 360800 —— 查证后确认
`config.acquire_lock()` 用的是 **msvcrt 文件锁**，进程死亡时锁自动释放，
文件内容只是"最后一次持锁者"的记录，不是活锁。PID 360800 已死
（EnumProcesses 确认），不影响下次启动机器人。无需清理逻辑——
文件锁的设计本来就防了这一手。（自检工具的 PID 检测走了三次弯路：
OpenProcess 对已回收 PID 误报存活、tasklist 的本地化"无任务"输出
破坏字符串匹配——最终 EnumProcesses 才是权威。）
