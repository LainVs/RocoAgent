# 检测方案 v2：材质优先

> 2026-11-20 · 基于 `logs/` 里 1846 张真实帧做的设计与回测
> 代码：`src/matdet.py`（检测器）、`scripts/backtest.py`（回测）、`scripts/probe_det.py`（单帧诊断）

## 0. 一句话

**现在的问题是"先假定 UI 在哪，再去读"；这套改成"先认出这是 UI 的哪种材质，再让它自己报位置"。**

前者一旦窗口大小 / 分辨率 / 版本变化就全错，而且**错得沉默**（读到墙也返回一个数字）。
后者错的时候一定返回 `None`。

这直接否掉了"把 ROI 从 `(166,170,244,20)` 换算成百分比"的做法。

## 2. 四种材质

| 材质 | 视觉签名（与位置、分辨率、美术无关） | 由它推导的元素 |
|---|---|---|
| **① 描边贴片 plate** | 半透明深色圆角块 + 上下一对**反向**的锐利梯度边 | 血条底板、能量槽、伤害胶囊 |
| **② 白字黑边 label** | 白笔画 + 深色描边，描边宽 ∝ 字高 | 名字、等级、`412/412`、倒计时、按钮文字 |
| **③ 白色贴纸 sticker** | 近白、低饱和、**云朵形**，含纯黑字 | 技能名牌、换人面板行、段位名牌、`开始挑战` |
| **④ 彩色圆徽 badge** | 高饱和小色块，拓扑 = 环 / 实心 / 带斜杠 | 属性徽章、编号 1-4、禁用符号、心、★ |

检测器的原子就这四个：

```python
find_slabs()      # ① 板：上下边缘配对 + 极性相反
find_labels()     # ② 白字黑边：tophat + blackhat 双形态学
find_stickers()   # ③ 白贴纸：分位数阈值 + 大核闭运算
find_disc_badges()# ④ 圆徽：白色圆片 + 中心必须有深色数字
```

8 个业务元素全部由它们组合。

## 3. 区域划分：按"锚"展开，不切蛋糕

```
┌──────────────────────────────────────────────────────────┐
│ [角锚-TL] 头像 → 名字 → 血条 → 能量行    [角锚-TR] 镜像     │
│              ↑ 一个锚点向下推导 3 个兄弟                    │
│ [中锚-TC] 倒计时                                           │
│ [侧锚-L] 编号圆 → 卡面 → 胶囊 → 禁用徽章 → 名牌             │
│              ↑ 5 个元素垂直堆叠，全部相对"编号圆"定位        │
│                    [中锚-BC] 按钮                          │
│ [角锚-BL] 聚能    [中锚-BC] buff 行     [角锚-BR] 菜单       │
└──────────────────────────────────────────────────────────┘
```

**置信度排序**（出问题先信谁）：
`白字黑边 > 描边贴片 > 白色贴纸 > 彩色圆徽`

**技能卡为什么锚在"编号圆"而不是"名牌"**：
编号圆四张完全一样、彼此孤立、尺寸固定、还自带 1/2/3/4 索引；
名牌是云朵形、和卡面底边粘连、按矩形滤会整组丢掉。实测两者命中率差一个量级。

## 4. 每个元素用什么方法

| 元素 | 方法 | 关键实现细节 |
|---|---|---|
| 血条底板 | Sobel 竖向梯度 → 长水平游程 → **上下配对且符号相反** → 板内梯度显著低于边缘 | 为什么不用颜色：建筑阴影同样"深色低饱和"，实测把整条吃进来 |
| 血条填充 | **列内彩色像素计数**（`S>110` 的比例 ≥ 22%） | 为什么不用分位数/Otsu：10px 高的条上白字占满条高，任何剖面统计都被字带偏 |
| 血条数值 | **读印刷数字**（我方 `cur/max`、敌方 `NN%`） | 像素在 10px 条上 1px = 0.8%，圆角端天然 ±4% 歧义；数字是精确值 |
| 技能卡 | 编号圆 → 卡面（4.3d × 4.6d）→ 胶囊（右下）→ 名牌（下方） | 比例常数由多帧实测得出，与分辨率无关 |
| 禁用状态 | 红色连通域的**拓扑**：有洞 = 红斜杠，实心 = 红三角 | 比模板匹配稳，不用维护模板库，还不怕缩放 |
| 倒计时 | 白字黑边 + 几何三元约束（字高 ∈ 2%~4.5%H、≤3 个块、水平居中） | 单独一个白块是噪声，三个约束一起用误报≈0 |
| 底部按钮 | 白色贴纸 + 贴纸内跑 3 个词模板，尺度由贴纸高度归一化 | 直接消灭"确认首发被 VS 护栏挡住"那类事故 |
| 力竭 | **缺席检测**：没有血条 + 没有技能卡 + 有心的数量 | 比 `my_pct<=0.5` 稳，也不受抓屏失败影响 |

## 5. 回测结果（`scripts/backtest.py`）

帧集与尺寸：

| 集 | 数量 | 尺寸 | 说明 |
|---|---|---|---|
| `shot/` | 400 | 1280×800 | 客户区 1:2，文件名带回合+动作 |
| `resultshots/` | 108 | 2560×1600 | 战斗中连拍 |
| `frames/` | 250 | 2586×1671 | 窗口帧（含 58px 标题栏，回测时裁成客户区） |
| `result_hit_` | 627 | 2586×1671 | 号称"结算页"，实际大部分是战斗帧 → 现成的误报负样本 |

实测（`--limit 30/20`）：

```
set=shot  30 帧 (1280×800，血条只有 ~10px 高)
  我方/敌方底板命中  93.3%  (28/30)
  4 张卡齐全         42.9%
  locate_hud         11.4ms  p95 18.5
  比例误差           中位 0.00pt（3 个 OCR 样本中 2 个为 0）
  离群              1 帧：血条左端被名字压住，配对只拿到半截

set=resultshots  20 帧 (2560×1600，血条 ~20px 高)
  我方/敌方底板命中   95.0%
  比例误差           我方 0.18pt / 敌方 3.08pt（12 个样本）
  locate_cards       96ms  ← 编号圆多档尝试，需要优化

set=result_hit  20 帧（号称"结算页"）
  我方 85%  敌方 80%
```

**最重要的一条结论：像素测量的精度与条高成正比。**

| 条高 | 比例误差 |
|---|---|
| 20px（2560×1600） | **0.2 ~ 3 pt**（够用） |
| 10px（1280×800） | 中位 0，但离群可达 ±20pt |

所以：**原生分辨率下像素够用；一旦窗口被缩到一半，就必须改走"读印刷数字"。**

最后一行 `result_hit` 本身也是一个结论：627 张里绝大多数其实是战斗画面，
说明旧的 `is_result_screen()` 误判严重——这批帧是现成的误报负样本。

## 6. 失败分析（诚实记录）

### 6.1 底板框会锁到"嵌套边"

一块血条有 **4 条水平边**：外框上、外框下、填充上、填充下。配对时若只拿到
"填充的那一对"，框就比真实底板窄 2~3px；若边缘合并把旁边的头像/编号圆粘进来，
框就偏左十几像素。

实测后果：`shot/120411` 里框偏左 16px，比例从真值 `0.95` 读成 `0.09`。
这不是"测量算法错"，是**框选错**，而框选错会让后面所有测量都白做。

### 6.2 我试过但**不成立**的三条

| 尝试 | 结果 |
|---|---|
| 逐像素时间方差找静态 UI | 全画面都在动，静态占比 0% |
| 绝对阈值找白贴纸（`S<40 & V>185`） | 4 张帧命中 0 |
| 按"条高 40%"内缩再量填充 | 满血读 96%、95% 读 100% |

### 6.3 当前还有的三个具体偏差（看着标注图就能定位）

| 现象 | 位置 | 修法 |
|---|---|---|
| **血条左端被名字/头像压住 → 只拿到半截** | `find_slabs` 的边缘配对 | 需要"只认数字字形"的字形库（§7.2），用字宽占比判残片。**已试两版都误触发**：血条高光本身满足"近白"，`_text_span` 会把整条读成字宽。所以 `fix_fragment()` 暂时**关闭**，代码保留 |
| **第 4 张卡框仍偏左**（1~3 张已对齐） | `locate_cards` 的虚拟行 x 插值 | 已改 `+1.30d` + 线性插值；第 4 张常是外推出的，x 会欠一点 |
| **2560 帧的卡检测 96ms** | 编号圆的 8 档尝试 | 每档都做一次形态学+连通域；改成"先缩小 ROI 再试"或只在前两档失败时才继续 |

另外两条**已验证有效**的修正（都写进代码了）：

- **`covers_text` 判据**：底板一定完整包住那行数字，且字上下有留白。
  内嵌边（被文字切开的上下沿）和能量 pip 行都包不住 —— 这一条把"
  嵌套候选"问题压下去一大半（144028 那帧从 0.00 修正到 1.00）。
- **`V>70` 附加条件**：有些皮肤的"空槽"是深棕色而不是中性灰，只按饱和度
  会把槽底当成填充（120411 敌方 0.639 → 0.475，真值 0.42）。

### 6.3 还在待定的

- **能量 pip 的语义**：`★10` 与 `★1` 都是"5 白 + 1 红"，说明 pip 不是能量。
  先用 `logs/litcap`、`eng0.png`、`eng10.png` 做一次"按 F 前后 pip 变化"的比对再定性。
- **换人面板样本只有 6 张**（`panel5.png` 等），不够标定。

## 7. 下一步（按收益排序）

### 7.1 用"数字字形行"做锚，反推底板框（⚠️ 试过，卡住，已记录）

目标：治"血条左端被名字/头像压住 → 只拿到半截 → 比例读成 0%"。

已经写好的部分（`matdet.refine_plate_by_glyphs`，代码保留、默认**关闭**）：
用字形行 bbox 定板心、向左右扫"板内是条色、板外 2px 立刻不是"。
这条"垂直一致性"判据确实能挡住头像（头像往外还是彩色）。

**真正卡住的是 `white_mask`：**

| 尝试 | 结果 |
|---|---|
| `V>190 & S<110` | 亮天空 / 白云 / 石阶同样是"又白又不饱和" → 字形行落到背景上（145014 那帧背景就是白云） |
| 加 tophat（`V - 局部中值 > 阈值`） | 血条的**1px 亮描边**整条被选进来 → 反而漏掉了数字 |
| 用原框高度当板高（不推 0.55） | 扫描行带落回正确位置了，但被上面两条污染的字形行还是错的 |

**要做对必须同时满足：**

```
白笔   <=>  V 高  ∧  S 低  ∧  tophat 强
深描边 <=>  blackhat 强（局部更暗）
⇒ mask = (V>170) & (S<115) & (tophat>t1) & (blackhat>t2)
其中 tophat/blackhat 的核 = 笔画宽度，需按字高自适应（≈0.12 × 字高）
```

这套就是 `matdet.find_labels()` 里已经在用的双形态学判据 —— 只是当时用的
核尺寸是按"band 高度"估的，没按"字高"估。下一步应该是把两者统一。

> 代价说明：`white_mask` 同时被数字字形通道用着，改动风险大。
> 所以这一条**先不动**，等数字通道在实机上跑稳再改。

#### 这一轮又试了两版（都已实现，代码在）

| 改法 | 结果 |
|---|---|
| `text_pixels()`：**逐连通域验证描边**（外面一圈比字暗 → 是字），完全不依赖笔画尺度 | 云/石阶确实被挡住了；但**精灵名字也有深描边**，靠形状分不开 |
| 加 `require_plate=True`：再外面一圈必须是"板上色" | 设计上正确（数字一定被底板包着），但 1280 那帧的候选块是 14px 高的**大块**（头像/名字），两圈都过 |
| `split_glyphs` 改成"多个候选行带、按文本性打分" | **有效**：修掉了"行带落到横线/基线"的 bug（145014 从"切到线段"变成能切出 7 个字） |

顺手修掉的两个真 bug（都在代码里，已生效）：

1. **"板外"取错了行**：原来只外扩 2px，而板高本身有 20% 的收缩，那 2px 还在板内
   → 整列都被判成"板外不是场景"，扫描永远不通过。改成取板边界之外 3 行。
2. **数字列把扫描截断**：数字压在板上，那些列"不是条色"，扫描到第一个数字就停。
   改成 `inside = max(条色比例, 文字比例)` —— 有字的位置对"是不是板"没有投票权。

#### 剩下的卡点（下一步）

`text_pixels` 现在能把"有描边的白字"找出来，但**名字/等级/道具数量也都是有描边的白字**。
唯一稳定的区分是"它被底板包着"，而这又需要知道底板框 —— 循环依赖。

打破循环的办法：**不修框，直接读字**。
血量这个字段其实不需要框：字形通道只需要"那一行字"的位置。

> 试过一次"把 crop 横向放宽到整条 HUD"，结果把**等级文字和 pip 一起切进来**
> （`412/412` 变成 `86%41277712`），已回退。
> 所以放宽不能盲目，必须同时限制"这一行"的 y 和"字的形状"。

下一步的正确做法：`read_bar_digits` 接受**带**，在带内按
"字高 ≈ 0.5~0.7 × 另一侧板高（镜像 UI，可靠）"挑行，
并在候选行上用"背景是条色"（`_bar_like`）做二次确认 —— 名字那行的背景是场景，过不了。

### 7.2 数值通道：字形模板（✅ 已完成）

`assets/digits_hp/templates.npz`：23 个 16×16 字形（`0-9`、`/`、`%`，每字 2 个变体）
`src/digitmat.py`：切字 → top-3 候选 → 束搜索 → 用像素比例当先验消歧

**自监督建库**（`scripts/build_digit_templates.py`）：

```
200 帧 → 447 个字形 → 82 个簇 → 23 个模板（每类保留票数最高的 2 个）
标注链：OCR 读出来 -> 解析 cur/max -> **切出的字形数 == 预期位数** 才采纳
       （这条把 OCR 的典型错法挡掉：分隔符被识别成数字、多加一位）
```

**为什么是"先聚类再投票"，不是"按位置贴标签"**：
按位置贴时，只要有一处斜杠粘连，后面所有字都会整体错位
（实测第 7 簇里把 4、5 都贴成了 7）。聚类后每个簇用多数票定名，少数派噪声自动被纠正。

**两条通道怎么合**（`digitmat.fuse`）：

```
字形读出来了  -> 用字形（精确值），像素只当"有没有读错量级"的守卫
两者差 > 3%   -> agree=False，上层可以拒绝出招
字形没读出来  -> 退回像素（±5%），标记置信度低
```

实测（原生 2560×1600，血条 ~20px）：

| 指标 | 结果 |
|---|---|
| 读率（至少一侧读出） | **68%**（`resultshots`）/ **100%**（`frames`） |
| 耗时（双侧，纯字形通道） | **4.5~11ms**（p95 20~32ms，首帧含模板加载） |
| 与像素通道一致（<2pt） | **92~100%**，中位差 **0.10~0.39pt** |
| 精度（对 OCR 真值） | 6/7 在 1.5pt 内，平均 **0.23pt** |

> 读率 68% 是**故意的保守**：加了结构校验 + 像素先验之后，
> 读不准的序列会被拒（返回 None）而不是给一个错值。

> **硬前提：血条高 ≥ 12px。** 1280×800 的帧（客户区 1:2 缩略图）里血条只有 9px、
> 数字 6px，切字必然失败——这不是算法问题，是分辨率问题。
> 结论：**感知必须用原生 2560×1600 的截图；缩略图只用于存盘/复盘。**
> （现在的 `_shot()` 存的是 0.5 倍縮略图，那是给人看的，别喂给检测器。）

### 7.3 性能

现在 `locate_hud` 37ms（1280×800），因为逐行 Python 循环 + 边缘对 O(E²)。
三条优化，按性价比：

1. **降采样到固定宽度再扫**（`find_bars` 已经这么做，`find_slabs` 还没做）→ 3~4×
2. **边缘表截断**：按游程长度取前 160 条（已做）
3. **事件驱动**：血条带没变化就复用上一帧结果（帧差只在 UI 带内算）→ 空闲帧 ~2ms

## 10. 真值评估（2026-11-20，人工读数 59 条）

### 10.1 为什么先做这个

之前的"精度"全是**两条通道互相一致**，而 OCR 真值自己就错 50%。
所以先建人工真值，再谈改进。

- 工具：`scripts/montage_hud.py` 把 HUD 条裁出、放大、编号拼图（**不画检测框**，避免被结论带偏）
- 标注：`logs/annot/labels.jsonl`，59 条，分四类
  `hp`（真血条+可读数字）/ `pip`（框落在能量行）/ `scene`（帧里根本没有血条）/ `cut`（数字被裁）
- 评估：`scripts/eval_det.py`（覆盖 / 中位误差 / ≤1pt / **错报** / 负样本误报）

指标里最重要的是 **错报**（报出了值但误差 >2pt）——机器人会照着错值行动。

### 10.3.1 这一版的两个新判据（都有真值支撑）

1. **`covers_text` 整带只算一次并缓存**：之前对每个候选都跑 `text_pixels`
   （2560 帧 160ms）。缓存后 50ms，覆盖率没掉。
2. **"均匀即闭嘴"**：先剔掉白字，取列中值的饱和度；若整条只有一种颜色
   （满血或空槽），**单帧无法靠颜色区分** → 用亮度粗判
   （`V>170` 判满、`V<140` 判空、中间返回 `None`）。
   这一条把负样本误报从 13% 压到 4.3%，且把红条 0% 从"读成 100%"修成 0%。

### 10.3.2 字形通道这一轮的三个改动（把 35% 提到 89%）

| 改动 | 为什么 | 效果 |
|---|---|---|
| **先放大再切字**（`digit_upscale`，目标字高 ~28px） | 1280 帧的血条只有 9~10px、字高 6~7px，直接归一化到 16×16 等于从 7px 硬拉，笔画粘在一起 | 字数切分正确率大幅提升 |
| **模板存全部样本 + k-NN 投票**（~400 个字形） | 每类 2 个质心不够：`354`→`95`、`100`→`78` | 单字准确率显著提升 |
| **分隔符用几何判定**（像素 x-y 相关系数 > 0.75 判为 `/`） | `/` 的形状和 `7`/`2`/`%` 太像，分类器必错；但斜杠是一撇，相关系数接近 ±1 | `149/542`、`417/417`、`118/417`、`43/316` 全对 |
| 切分间隙 0.16 → **0.10**（× 条高 × 放大倍数） | 间隙太大会把相邻数字并成一个（`542`→`52`） | 五张难帧的字数全部正确 |

### 10.5 方法学规矩（以后都按这个来）

```
1. 任何"改进"必须跑 scripts/eval_det.py，看 ≤1pt 和 错报，不看"一致率"
```

### 10.6 关于"卡面伤害"的口径（2026-11-20 修正）

**卡面上的数字是系统算好的伤害**（含对面防御/buff 系数、我方加成、克制），
可以直接当"真实伤害"用。这让"反推对面精确血量"变成一行式子：

```
M = 100 × 卡面伤害 / 掉血百分点
```

实测同一场两次不同技能：`425 → 46.9%`（M≈906）、`467 → 51.9%`（M≈900），
**差 0.7%**，说明关系成立。误差主要来自百分比取整：Δp 越小误差越大
（Δp=3.7 时 M 会飘到 2700）。

估计器要点（留给 P4 实现）：

```
观测：每次命中 (卡面伤害 D_i, 掉血 Δp_i)
模型：Δp_i = 100·D_i/M + ε,  ε ~ U(-0.5, 0.5)
加权：w_i ∝ 1/σ_i²，σ ∝ 1/Δp     ← Δp 大的事件权重高
守卫：有效事件 < 2 或 σ_M/M > 5% 只输出区间；与物种先验矛盾则判数据不可信
```
