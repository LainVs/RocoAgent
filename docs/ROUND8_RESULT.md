# 本轮结果：身份门禁 + 覆盖率量化（2026-11-23 10:xx）

## 已完成的两处修复

### 1. 候选词表改为「配置 ∪ 可学池」并集

上一轮"配置优先独占"引入的回归：

```
09:28:16 BAND -> 音速犬 槽1 未识别 (conf 0.00 < 0.80) raw='香噬' vocab=4(config)
```

`香噬` 是「吞噬」的形近误读。而「吞噬」在音速犬**可学池**里、
**不在配置**里（用户实机换过技能）。配置独占把这条路堵死了。

两个数据源漏的地方正好相反，所以必须取并集：

| 场景 | 配置有? | 可学池有? | 谁能救 |
|---|---|---|---|
| 「扬沙」卡瓦重 | ✅ | ❌ | 配置 |
| 「吞噬」音速犬 | ❌（表过期） | ✅ | 可学池 |

顺带修掉一个静默陷阱：门槛 `0.80 if len(vocab) < 60 else 0.90` 会随
词表规模**突然跳变**，而 `Ocr.match` 的分数与词表规模无关 —— 词表一变
大，同一个匹配就会从"采纳"变成"拒绝"，没有任何提示。
改为统一 `BAND_MIN_CONF_BAND = 0.80`。

### 2. 换人后身份未确认 -> 禁止 BAND

```
09:46:14 PET -> 音速犬 (ONNX 1.00)      <- 最后一次成功识别
09:46:39 BAND -> 音速犬 槽1 raw='叠浪'   <- 连拒 3 次
09:48:58 FORCED SWITCH -> panel is up   <- 场上换过精灵
09:49:05 PET -> 恶魔狼 (ONNX 1.00)
```

「叠浪」属主仅 9 只、全是水系，音速犬（火系）学不了。dump 图确认卡面
真是「叠浪」（蓝色水系美术），而同槽位早前读到的「反击拳」是橙红拳套
—— 不可能是同一只精灵。

同窗口 `unknown bust` 出现 **9 次**，ONNX 持续失败，`my_name` 卡在旧值。

**真正的危险不是"读不出"，是"碰巧命中"**：槽2/槽4 读到的「诋毁」
「闪光冲击」恰好音速犬也有，差点把错配数据写进 `session_moves`
污染策略。数据佐证：`叠浪 ∩ 闪光冲击 = 空集`，没有任何精灵能同时
学这两个 —— 说明槽1 与槽4 读到的东西不属于同一只精灵。

**为什么不用时间门禁**（原方案已废弃）：

```
我方身份事件：成功 40 / 失败 22（35% 失败率）
成功识别间隔：中位 103s，均值 262s，90% 超过 20s
```

ONNX 在战斗中本就稀疏，20 秒时间门禁会误伤 90% 的正常机会。
改用**换人信号**：主动换人 / 强制换人 / 新对局三处置
`_ident_confirmed = False`，下次成功识别才置 True。
代价只有换人后 1~3 秒，而那正是 `pet_at` 1.2s 窗口本来也会跳过的区间。

旧模板兜底通道**不能**置 True —— 它的标签已证伪。

## 覆盖率量化（这是本轮最有价值的数字）

```
BAND 总尝试 57 次
  采纳 11 / 拒绝 46
  其中 32 次是空读数（状态卡/无名字卡，属正常）
有效尝试 25 次，命中 11 次 = 44.0%
```

拒绝分布：

| 词表层级 | 次数 | 判断 |
|---|---|---|
| `?`（空读数） | 32 | 正常，状态卡无名字 |
| `config` | 7 | **正确拒绝** —— 配置里真没这个词（用户换队） |
| `config+species` | 7 | 需逐个核查，这才是可改进的真问题 |

`near-unique` 兜底贡献了 3 次采纳（约占 27%）。

## 未完成：更权威的数据源（已探明但未接入）

发现 `data/external/rkpp-official/skillbanks.json` —— **官方 PAK 解包**的
"精灵 -> 等级 -> 可学技能池"，共 **16828** 条，比 `species_skills`
（40k 行但残缺）更接近真相。

问题：`banks` 的键是官方图鉴编号（`160301` 这类 6~9 位），与主库
`species.id`（`3042` 这类）不是同一套，需要一层 id 映射才能用。
`pokedex_800_pvp_usage_v340.json` 里 id 也是主库那套，两者对不上。

**下一步方向**（如果继续做）：找到官方编号与主库 id 的对应关系，
或者干脆只用 skillbanks 的"技能池"做校验（不需要精确到某只精灵，
只要判断"这个词是不是某个精灵的可学技能"也够）。

## 为什么不继续深挖

44% 的有效命中率里，`config` 那 7 次拒绝是**对的**（配置过期就该拒）。
剩下的 7 次才是真问题，而且已经定位到数据源残缺（`species_skills`
对「扬沙」「岩脉崩毁」这类常见配法都缺）。

继续改的收益递减，而风险在上升：每放宽一次门槛就多一分误配风险，
而误配的代价（污染 `session_moves` -> 影响策略）远大于偶尔漏读。

**建议先让用户跑一次 `team_db` 更新配置** —— 那 7 次 `config` 拒绝
会立刻消失，命中率能到 70%+，成本远低于继续改代码。
