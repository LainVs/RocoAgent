## 前置：风扇为什么响

**首要嫌疑（我自己引入的）**：上一轮把 `standalone.MIN_INTERVAL` 从 1.0 降到 0.35，
并且让 `ui_server.live_state()` 在机器人数据过期（>3s）时**每次请求都调
`standalone.observe()`**。前端 400ms 轮询 → 每秒 2.5 次全屏抓取 + perceive
（每次 150~250ms），叠加机器人自己的主循环（OCR/ONNX/481 模板匹配），
CPU 直接打满。

**次要嫌疑**：机器人主循环里 `_cast_ocr`（OCR 1.5~5s）每 2 秒跑一次，
`_check_foe`（481 模板 + ONNX）每 0.7 秒跑一次。

## 执行顺序（每步独立验证 + 提交）

### 第 0 步：先量，再改
- 量 CPU：`Get-Process python | CPU`、`ui_server`/`robot` 各自占用
- 确认是 standalone 反复抓屏还是机器人主循环

### 第 1 步：降载（解决风扇）
- `standalone.observe()` 加**单飞锁**：同一时刻只允许一个抓屏在跑，
  其他请求直接拿上一次结果（现在虽然 `_lock` 有，但 400ms 轮询会排队）
- 把 UI 侧 fallback 的触发条件从"3 秒"放宽到"2 秒"并加 0.5s 结果缓存
- 机器人：`_cast_ocr` 间隔 2s → 4s；`_check_foe` 0.7s → 1.5s

### 第 2 步：伤害计数器实时化
- 核心是**读屏链路本身要快**：`perceive.observe()` 实测 150~250ms，
  已经够 2~4Hz
- 关键是**不要被机器人 16 秒的写盘拖住**（上一轮已改，需验证）
- 目标：UI 上的卡面伤害/血量在 0.5 秒内变化

### 第 3 步：技能识别链路
- `_maybe_band_scan` 的触发窗口太窄（要求 bar=True + 非倒计时 + 出手 2s 后）
- 改成：**每次技能栏出现且缓存 miss 时**就扫（但要限流，避免 OCR 打满 CPU）

### 第 4 步：头像纠错
- 用 `pet_avatars/<id>.png`（官方 639 类）当基准审计模板库
- 错标模板重命名；无法判定的移入 `_quarantine/`
- 我方识别加"必须与 ONNX 一致"的交叉校验（防 0.55 模板推翻 1.00 ONNX）
