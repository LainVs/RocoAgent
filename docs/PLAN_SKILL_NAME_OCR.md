# 计划：卡面技能名读取（能力边界报告）

> 2026-11-21 · 代码：`src/skill_names.py`、`src/test_skill_names.py`
> 结论先说：**受限词表纠错可行，纯 OCR 不可行。**

---

## 0. 为什么要做这个

`perceive.attach_skill_names()` 现在的做法是从 `my_team` 表按**槽位顺序**
猜技能名 —— 完全信任队伍配置。

`docs/PLAN_SKILL_KIND.md` 把配置过期列为"最隐蔽的 bug"：配置里写「借用」，
实际卡面是「火云车」，于是 power=0 的判定作用在错误的槽位上，表现为
"策略选了低伤害技能"，很容易误判成策略 bug。

而卡面上**印着名字**，所以这件事理论上可以根治。

---

## 1. 名字条在哪（标定）

名字条 = 米白椭圆底 + 深色艺术字，位于伤害胶囊**左侧偏下**。

实测 4 个槽位（`logs/bar_partial_093057.png`，530×1040 技能栏裁剪）：

| slot | 伤害胶囊 (x0,y0,x1,y1) | 名字条实际 (x0,y0,x1,y1) |
|---|---|---|
| 1 | 245,226,312,254 | 183,252,324,292 |
| 2 | 201,405,267,437 | 139,435,281,480 |
| 3 | 229,587,291,622 | 167,620,311,673 |
| 4 | 322,744,385,784 | 260,792,410,848 |

规律：**左边 ≈ 胶囊左边 − 62，上边 ≈ 胶囊底边 + 8，宽 150，高 56**
（卡面倾斜会上下浮动 ±12px，所以窗口给足）。

### 1.1 定位文字的两个坑

**坑 1：不能用"深色像素"当文字掩码。**
卡面背景本身就是暗的，整窗都是"深色"，收紧完全失效 ——
实测 `rowsum` 最大值 = 窗口全宽，包围盒永远是整个窗口。

**坑 2：名字条底板是关键中间层。**
先找米白底（三通道都高且彼此接近），再在底板里找深色字。
卡面图案再暗也不是米白；而名字条不管倾斜多少度都是米白。

**坑 3：底板里左边可能有图标。**
slot3（蝙蝠）的底板左边有粉色图标，直接取包围盒会让文字只占 40% 宽度，
OCR 直接放弃。按**列投影**切出连续文字带（允许 3 列以内空隙）可以排除图标。

## 2. 核心思路：受限词表纠错，不是开放式 OCR

每个槽位的候选**只有 4 个** —— 就是我方这只精灵配的 4 个技能。
所以不需要"认出整串字"，只需要「在这 4 个候选里挑最像的」。

实测匹配效果：

```
OCR='火焰切割'   -> 火焰切割  1.00
OCR='惊吓盒'     -> 惊吓盒子  0.85   少一个字，靠候选补回
OCR='火云'       -> 火云车    0.85
OCR='吞'         -> 吞噬      0.55   首字唯一时采用
OCR=''           -> None      0.00   拒绝
OCR='xxx'        -> None      0.00   拒绝
```

`match_candidate()` 的打分：

| 情况 | 分数 |
|---|---|
| 完全相等 | 1.00 |
| 候选是 OCR 的延长（OCR 短了） | 0.85 |
| OCR 是候选的延长（OCR 长了） | 0.85 |
| 公共前缀 ≥ 2 字 | 0.60 |
| 公共前缀 1 字（仅候选里唯一时） | 0.55 |
| 其他 | 拒绝（< 0.55） |

**宁可留空，也不要写错** —— 分数 < 0.55 一律返回 None。

---

## 3. 现实：OCR 引擎的能力上限

这是本次最重要的发现，必须记下来。

RapidOCR 对这套小尺寸艺术字的**中文**识别能力有限。同一帧
`logs/bar_partial_093057.png`（4 张卡，肉眼都很清楚）：

| slot | 真值 | OCR 结果 | 匹配 |
|---|---|---|---|
| 1 | 吞噬 | `吞噬` | ✓ 1.00 |
| 2 | 火焰切割 | `火焰切割` | ✓ 1.00 |
| 3 | 蝙蝠 | **空** | ✗ |
| 4 | 惊吓盒子 | `惊吓盒` | ✓ 0.85（靠候选补回） |

**3/4 可用**，但 slot 3 在任何条件下都读不出。

### 3.1 排除"是我预处理错了"

试过的所有组合，全部失败：

| 尝试 | 结果 |
|---|---|
| 缩放 1.0 / 1.5 / 2.0 / 3.0 / 4.0 / 6.0 | 全部空 |
| 二值化（Otsu）+ 白边 | 空 |
| 旋转 −20° ~ +20°（每 3° 一档） | 空 |
| `read_line`（跳过检测直接识别） | 空 |
| 灰度 / 彩色 | 空 |

**决定性对照**：用 cv2 字体渲染同样几个词（黑字白底、1.8 倍字号）：

```
蝙蝠     -> '????'
吞噬     -> '????'
惊吓盒子  -> ''
火焰切割  -> ''
```

连系统字体的黑字白底都读成 `????` —— **不是裁剪、不是预处理、不是倾斜，
是识别模型对这些字的覆盖不足**。

### 3.2 所以这个模块的定位

**辅助校验，不是权威来源。**

- 读到高分（≥ 0.85）时，可以用来发现"配置和卡面不一致"
- 读不出时不报错、不阻断，返回 `None`
- **绝不**用 OCR 结果覆盖队伍配置
- 单次约 0.4s（× 4 槽 × 最多 3 次），只能放后台线程或开局跑一次

---

## 4. 为什么还是值得留下

即使只有 3/4，它的价值是**发现配置漂移**：

```
配置里 slot2 = 火云车
卡面读到   slot2 = 火焰切割  (1.00)
          -> 高置信度不一致 -> 告警，提示人工核对 my_team
```

这类错误现在完全静默（`attach_skill_names` 无条件相信配置），
而它会让 power/能耗判定整体错位。

反过来，读不出时保持静默 —— 那只是"这次没验成"，不是故障。

---

## 5. 测试

`src/test_skill_names.py`（21 项）**只测匹配逻辑，不测 OCR**：

> 把"OCR 认对"写进测试只会得到一个随机失败的套件。真正需要钉死的是
> 匹配规则：给定一个不完美的 OCR 结果，必须在 4 个候选里挑对，或者
> 明确放弃。

覆盖：
```
[1] 完全相等
[2] OCR 少字（候选更长）
[3] OCR 多字（OCR 更长）
[4] 只读到首字
[5] 必须拒绝的情况（空 / 无关 / 首字唯一才可采用）
[6] 单字候选不能吃掉长名字
[7] 歧义时不瞎猜
[8] 候选归一化（字符串不能被拆成字符）
[9] 名字条窗口几何（含边界裁剪）
```

## 6. 还没做 / 后续方向

- **接入主循环**：现在只是命令行工具。要接的话应该是「开局时在后台线程
  读一次，和配置对账，不一致就写日志 + 在控制台标黄」。不能每帧读。
- **换 OCR 引擎**：如果以后要真正读卡面名字，需要能认这类艺术字的模型
  （合成训练数据微调，或换 PaddleOCR 的中文模型）。本次没做，因为
  引擎能力是外部约束，不是本项目能快速解决的。
- **替代方案**：比读名字更可靠的是**读卡面伤害数字 + 查技能表反推**。
  已经知道每个候选技能的 power 和克制关系，理论上能从"读到 175"反推出
  是哪个技能。但这需要更准的伤害模型，且数字识别本身也有 2.7% 的误差。
