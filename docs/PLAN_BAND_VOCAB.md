# 计划：修 BAND 词表缺「扬沙」—— 两级词表（配置优先于可学池）

## 铁证

`--band-dump` 落盘图 `band_卡瓦重_2_1795392346_ctx.png`：

```
[火][60]  ← 胶囊（60 伤害）
   扬沙   ← 名字带，清楚可见
```

`my_team` 槽3 配置 = `[筛管奔流, 扬沙, 虫击, 冰雹]`，槽2 正是**扬沙**。

而日志：

```
08:05:51 BAND -> 卡瓦重 槽2 未识别 (conf 0.00 < 0.80) raw='扬沙' vocab=58
08:06:03 BAND -> 卡瓦重 槽2 未识别 (conf 0.00 < 0.80) raw='扬沙' vocab=58
08:06:18 BAND -> 卡瓦重 槽2 未识别 (conf 0.00 < 0.80) raw='扬沙' vocab=58
```

**OCR 三次都读对了「扬沙」，但 `conf 0.00` 拒掉了。**

## 根因：`species_skills` 数据不全

```
物种查询: species WHERE name='卡瓦重'
          -> id 3042 / 3294 / 3295 / 3296  （同名 4 行！）
species_skills 查询: 这 4 个 id 的技能并集 = 58 个
          -> 含「筛管奔流」= True
          -> 含「扬沙」     = False   ← 但游戏里确实带着
```

「扬沙」的属主有 **147 只**，其中包含 `卡瓦重（雪山附近的样子）`
（另一个变体 species 行），但**基础名 卡瓦重 名下没有挂这条**.

也就是说：`species_skills` 漏了合法的配法组合。用��名查会跨多个变体
id 取并集，但这个并集本身就不完整。

## 为什么不能简单放宽门槛

如果为了放过「扬沙」而降低门槛（0.80 -> 0.30），会立刻引入误配：
「扬沙」是全库 1045 个技能里的常见词，`扬沙x`、`扬沙` 之类的近似
都可能命中别的技能。**安全性不能丢。**

## 修法：两级词表，把 `my_team` 配置放第一位

`my_team` 的 `moves` 是**用户亲手配的**，是最强证据：

1. **第一级**：这只精灵在 `my_team` 里的 4 个技能（精确 4 个词）
   - 词表极小 -> 门槛 0.80 已经足够（分母小，1 字偏差分数高）
   - 且**不可能配错**（只有这 4 个候选）
2. **第二级**：`species_skills` 池（几十个）
3. **第三级**：全库（1045 个）

实测对照（本次数据）：

| 精灵 | 配置 | BAND 观测 | 是否在配置内 |
|---|---|---|---|
| 卡瓦重 | 筛管奔流/扬沙/虫击/冰雹 | 扬沙(槽2) | **是** |
| 冰钻布鲁斯 | 丢冰块/暗突袭/主轴/扬沙 | 先发制人(槽2) | 否 |
| 恶魔狼 | 吞噬/火焰切割/蝙蝠/惊吓盒子 | 先发制人(槽1) | 否 |

第一级能解决「扬沙」这种"配置有、库里没有"的漏配。
配置里没有的（后两只的「先发制人」）说明用户实机改过队伍，
那种情况继续落到第二级（species_skills 池）—— 而「先发制人」
有 193 个属主，池里通常有，所以能过。

## 附带修：同名多 id 导致的池污染

`species WHERE name=?` 会跨 3042/3294/3295/3296 取并集，混入别的变体
技能。应该只在**必要时**才用这种宽查询。第一级用 my_team 配置就绕开了
这个问题。

## 验收

1. 卡瓦重槽2 能读出「扬沙」（conf >= 0.80，词表=配置 4 词）
2. 不引入误配：`test_session_moves` 的 `扬沙x` -> `扬沙` 之类用例仍按
   门槛判定
3. 新增回归：配置优先特征表（用 FakeScreen + 合成名字带）

## 不做的事

- 不修 `species_skills` 的 40k 行数据（来源不明，改动风险大）
- 不放宽总门槛（会引入误配）
