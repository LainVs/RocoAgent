## 2. 三种状态（含一个坑）

| 状态 | 实测填充色（填充根部中位色） | 判定 |
|---|---|---|
| 满/正常 | 亮绿 `(115,198,21)` | `G ≥ 1.1R` |
| 残血 | 橙黄 `(251,181,65)`（38% 时）、红 `(175,61,62)`（7.4% 时） | `G ≥ 0.55R` 记橙，否则红 |
| 倒下 | 内槽全空、无亮填充；外框底板仍在 | `ui=True 且 pct≤1` |

颜色切换点没抓到边界帧，只能说 **大约 50% 由绿转橙、20% 以下转红**（有 38% 橙、44.7% 橙、
23% 红、7.4% 红几个样本一致，但阈值本身没验证）。所以 `hp.jsonl` 的判定走血量数字
（`LOW_PCT=35`），颜色只写进 `timeline2.txt` 辅助看。

### 两个必须知道的坑

1. **空槽不是黑的，是填充色的暗版本。**
   红血条 7.4% 那帧，亮填充 `(174,61,62)`，而空槽是 `(118,34,35)` —— 饱和度 84、亮度 118。
   只按"高饱和"取填充，会把整条空槽算进去，7.4% 直接读成 44%。加一道亮度门
   （`max(R,G,B) > 145`）后就准了：亮填充 max≥170，暗槽 max≤120。

2. **血条上压着 `345 / 345`、`23 %` 的白字，深色描边会把填充切断成 2~3 段。**
   按"每列至少 2 个亮像素"统计即可跨过文字（文字上下两行仍是纯色），不用补洞；
   填充右端正好落在文字正下方时误差约 1~2%（38% 读到 39.3%，真值 39.13%）。

3. **换人时血条有滑入动画。** 新宠的血条是一边出现一边变长的，第一帧左端可能从
   `x=+9` 才开始，这时读数会变成 0%。`read_bar()` 里有"左端必须贴住 x=0（容忍 6px）"
   的门槛，遇到这种情况直接返回 0 —— 所以**单帧读到 0 不等于精灵倒下**，必须看
   下一帧（见第 5 节）。

## 3. hpwatch.py

```
python D:\Tools\hpwatch.py                 # 常驻，0.5s 一次 -> logs\hp.jsonl
python D:\Tools\hpwatch.py --duration 300  # 限时
python D:\Tools\hpwatch.py --once          # 读一次，打印一行
python D:\Tools\hpwatch.py --analyze D:\Projects\RocoAgent\logs\frames2
python D:\Tools\hpwatch.py --selftest      # 4 张已知战斗帧回归 + 菜单帧误判检查
```

- `hp.jsonl` 每行：`{"ts","my_pct","foe_pct","判定"}`。非战斗时 pct 为 `null`、判定
  `no_battle`；窗口找不到时判定 `no_game:...`，进程不退出；每行都 `flush()`，随时可 tail。
- 判定取值：`no_battle` / `normal` / `my_low` / `foe_low` / `both_low` / `my_dead` /
  `foe_dead` / `both_dead`（`low` = ≤35%，`dead` = ≤1%）。
- 离线分析用 6 进程并行解码：单进程 600 帧要 4 分钟，并行约 40 秒。
- `read_bar()` 同时吃两种输入：离线 PNG（RGB）和 live 抓屏（`capture.grab_rel()` 返回
  的 BGR，翻转成 RGB 再算）。

## 4. 时间线（logs\timeline2.txt）

`--analyze` 每帧一行，事件列标 `我方掉血 / 我方回血 / 敌方掉血 / 敌方回血 /
【归零/倒下】/【换人】/战斗开始 / 非战斗`。阈值：掉血 ≥2 个百分点、回血 ≥3 个百分点，
挡掉 ±1.5% 的测量抖动。

真实战斗窗口不好等：抓帧目录只留最新 600 帧（约 4 分钟），战斗又是间歇性的。

### hp.jsonl 里的活数据

常驻进程实测：0.5s 一次，02:36:29–02:42:10 抓到 679 条战斗样本（我方 55.7%，
`判定=normal`）。这段数值一直没变，是因为游戏停在回合倒计时等我方出手、一直没人操作，
不是读死了 —— 同刻截图 `地绡银龙 217/391 = 55.5%`，读数对得上。

另外这台机器上 python 常驻进程会被外部周期性杀掉（抓帧链重启），`hpwatch.py` 本身
不退出、但进程没了就断档；日志里 02:00–02:12、02:33 的缺口都是这个原因，不是脚本崩了。
真要长期跑，套一层重启循环（我临时用的 `keepwatch.py` 就是这么干的）。

## 5. 能否从血量曲线自动识别「我方倒下 → 强制换人」

**能。**判据不是单点"掉到 0"，而是「归零 → 停一段 → 满血重现」这个三段式，
两个正例都已经在真实数据里抓到（上面 02:13:20 → 02:13:58）。

三条同时成立才判换人：

1. 我方 pct 从 >1 掉到 ≤1，且**下一帧仍在 0**（掉到 0 一帧就立刻满血回来的是血条
   滑入动画，不是倒下——02:12:02 敌方换人就是这种，新宠血条从中间开始长）；
2. 我方 pct 回到 >90%；
3. 距倒下 ≤90 秒，且**敌方 pct 与倒下时刻相差 <10 个百分点**（排除整场战斗重置 / 新一场开始）。

反例必须挡掉的两类：

- **技能动画 / 切场景**：整个战斗 HUD 消失，血量读不出来 —— 先靠"外框灰边是否在场"挡掉，
  再看缺席长度（≤12s 当作同一次战斗延续，>12s 算新一场）。旧 `timeline.txt` 里成片的
  `my=0 foe=0` 全是这个原因，旧代码没有这道门。
- **治疗回满**：起点是残血不是 0，且中间没有归零帧（02:12:31 的 33.6→45.1、02:18:32
  的 33.2→41.8 就是治疗，没有被误报成换人）。

局限（老实说）：

- 「强制换人」和「玩家主动换人」「复活」的血量曲线一模一样，光看血量分不开。要区分得
  联合技能栏/回合数，或者看换人后精灵名字（`name.png` 那套 OCR）。
- 换人动画期间血条会消失 5~50 秒（02:13:58 那次断档 38s），所以"倒下 → 满血"的时间差
  给到 90 秒比较稳，但这也意味着**两次换人如果间隔 <90s 会被合并**。
- 敌方换人同样适用（02:12:02.168 那帧就是敌方换人时的血条滑入，已按"动画"处理，
  不再误报成"敌方归零"）。
