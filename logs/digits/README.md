## 2. 为什么不用 OCR

数字是 14×17 像素的艺术字，压在**纯色** `(61,61,61)` 的胶囊底上。
Windows OCR 对这么小的彩色描边字完全无效。

但「底色纯 + 字色纯」意味着可以做 alpha 反解：

```
pixel = a × C_text + (1 - a) × C_bg
a = ((pixel - C_bg) · (C_text - C_bg)) / |C_text - C_bg|²
```

`a` 就是字形覆盖率，天然抗锯齿。再乘一个颜色闸门（防止卡面的浅蓝/浅紫
被当成字）就得到干净的二值图。

**这里有三种字色，第一版漏了第三种：**

| 字色 | RGB | 含义 |
|---|---|---|
| 绿 | `(134,217,93)` | 增益后 |
| 红 | `(198,73,74)` | 减益后 |
| **白** | `(245,238,225)` | 无增减（和技能名牌同色） |
| `--` | 同白色，但只有两道横杠 | 无威力（变化类技能） |

白字和名牌同色，所以不能只靠颜色区分。解决办法：先把胶囊底
`(61,61,61)` 的连通域填实、再腐蚀 3 像素，得到「胶囊内部」遮罩，
只在这个遮罩里找字——圆角处露出来的名牌米色就被挡掉了。
「`--`」和数字的区分靠几何：横杠高度只有 6 像素，数字 14~20 像素。

## 3. 界面结构

```
┌─ ★3 ────────┐   ← 左上角「★N」徽标（底色一样，要排除）
│   技能图标   │
│        84   │   ← 右下角伤害胶囊（要读）
└─────────────┘
   技能名
```

星标和伤害胶囊**底色完全相同**（都是 `(61,61,61)`），靠「星标里有黄色
星星」区分。实测黄色像素数：星标 159~223，伤害胶囊 0。

定位流程：

1. 在 `x∈[250,780], y∈[480,1520]` 内找纯色 `(61,61,61)` 连通域
2. 尺寸/宽高比过滤（实测 61~69 宽、27~42 高，宽高比 0.43~0.68）
3. 含黄色 ≥40 像素 → 星标，丢弃
4. 用胶囊内部遮罩切字，切得出数字尺寸的字块 → 伤害胶囊
5. 切不出但有亮像素 → 「--」；都没有 → 背景装饰，丢弃
6. 按 y 排序 = 技能 1~4

这套判据在 860 帧非战斗画面上**零误报**（排位等待界面曾误报一次，
已用尺寸+字块约束修掉，那张帧保留在 `digits\frames\` 里当负样本）。

## 4. 字形模板

- 切字：连通域，只留高 9~32、宽 3~28、面积 ≥14 的块
- 归一化：紧致外接框缩放到 **14×18**，另存宽高比 `w/h`
- 卡片有倾斜（不同卡角度还不一样），每个原型额外生成 **±8° 旋转副本**

**标注怎么来的（这是本方案最关键的一步）：**

人工只标注了 5 帧真值（两张绿字帧 + 三张肉眼核对过的白字帧），
得到 53 个种子字形。剩下 840 个字形用**两个独立信号交叉验证**自动扩：

1. 无监督聚类（相关度 ≥0.86 归一类），得到 16 个形状类
2. 用种子模板给每个类投票，投票一致率 ≥92% 才整类接收

两个信号在全部 16 个类上 **100% 一致**，说明「同一个字形的所有出现
长得一样」这个前提成立。最终 893 个字形，10 个数字类别全齐。

原型挑选用的是 **k-center（最不像的优先）**，不是「最典型」的——
第一版按典型度挑，结果所有 0 原型都来自同一个倾角，换个角度就把
`140` 的 0 认成了 8。改成最不像优先后修好。

**数字 9 没有真实样本**，用「6 旋转 180°」合成，`report.json` 里标了
`synthetic_9: 1`。

## 5. 用法

```powershell
# 读一张截图（可多张，-j 出 JSON）
python D:\Tools\digitread.py read D:\Projects\RocoAgent\logs\digits\frames\020511_305.png
```

输出：

```
== 020511_305.png  visible=True
   skill 1: --     kind=dash   score=1.00
   skill 2: 425    kind=num    score=1.00 green
   skill 3: 70     kind=num    score=1.00 white
   skill 4: 100    kind=num    score=1.00 white
   order: 2 > 4 > 3 > 1   (2=425  4=100  3=70  1=--)
```

`order` 就是「四个技能伤害从大到小」，`--` 永远排最后。

| 命令 | 作用 |
|---|---|
| `read <图...>` | 读数值 + 排序 |
| `scan <目录...>` | 列出技能栏可见的帧 → `frames.txt` |
| `watch [秒数]` | 盯 frames2，把战斗帧复制到 `digits\frames\` |
| `build` | 重建模板 + 拼贴图 + 裁图（含自动扩充） |
| `selftest` | 留一 + 跨来源验证 |
| `cv` | 留帧验证（用其余帧建模板，读被留出的那帧） |

代码里调用：

```python
import sys; sys.path.insert(0, r"D:\Tools")
import digitread
r = digitread.read_image(r"...\frame.png")
r["visible"]                     # 技能栏是否可见
[s["value"] for s in r["skills"]]  # [None, 425, 70, 100]
r["order"]                       # [2, 4, 3, 1]
```

`score` 是置信度：<0.75 建议复核，`?` 表示该字形没认出来
（会自动降级成按位数比较，不会瞎给数字）。

## 6. 实测结果

**定位**：112 张保存帧中 110 张判定为战斗帧（另 2 张是排位等待/过场，
正确拒绝）；860 帧非战斗画面零误报。

**读数（用全部数据建的模板，5 张已标注帧）**：

| 帧 | 真值 | 读出 | 排序 |
|---|---|---|---|
| skill_001 | 84/66/540/-- | 84/66/540/-- | ✓ |
| skill_002 | 140/110/112/-- | 140/110/112/-- | ✓ |
| 020511_305 | --/425/70/100 | --/425/70/100 | ✓ |
| 020625_010 | --/212/70/100 | --/212/70/100 | ✓ |
| 020700_003 | --/425/70/100 | --/425/70/100 | ✓ |

**时间一致性**（最强的间接证据）：108 张战斗帧读下来只有 3 种结果，
且是连续的段：

```
-- / 425 / 70 / 100   53 帧
-- / 212 / 70 / 100   17 帧   ← 只有技能 2 变了，且正好减半
-- / 425 / 70 / 100   38 帧
```

随机错字不可能产生这种结构：如果 425 的某个数字读错，其它三个技能不
该保持不变，更不会刚好出现「减半又恢复」。

**字形分类**：

| 验证方式 | 结果 |
|---|---|
| 留一交叉验证（52 个手工标注字形） | 51/52 = **98.1%** |
| 跨来源（绿字训练 → 白字/2 倍图测试） | 8/9 = **88.9%** |
| 留帧验证：数值完全读对 | 17/20 = 85.0% |
| 留帧验证：四技能排序正确 | 4/5 = **80.0%** |

留帧验证唯一的失败是 `skill_001`（84/66 读成 34/55）：因为把这一帧
留出后，训练集里**根本没有 6 和 8**，只能就近乱认。这不是算法问题，
是覆盖度问题——而实战中这一帧本身就在训练集里。

## 7. 明确回答

**能不能给出四个技能伤害从大到小的排序？能。**

- 用现有全部数据建的模板，5 张已标注帧**排序 5/5 全对**，数值 20/20 全对
- 留帧方式做真实外推：排序 4/5，数值 17/20
- 108 帧实战序列读数完全稳定

准确率估计（干净战斗帧、四张卡都在画面里）：

| 指标 | 估计 |
|---|---|
| 技能栏定位 | ~99%（110/112 命中，860 帧负样本零误报） |
| 单个数字分类 | ~95% |
| 三位数完整读对 | ~85% |
| **四技能排序正确** | **~90~95%** |

排序比数值准，因为只有两个技能的数值被读错到互相越过时才错。
`score` 可直接当置信度用。

剩余风险，按严重程度：

1. **数字 9 是合成的**，没有真实样本验证
2. 数字 3 只有 4 个样本（全部来自星标白字），6/8 各只有 1~2 个
3. 五位数、或技能卡被技能特效大面积遮挡时的表现未验证
4. 两场战斗的界面倾斜角不同，如果第三场角度差更多，可能退化成 `?`

## 8. 怎么继续提升

挂 `watch` 再抓几场，把数值肉眼填进 `manifest.json`，重跑 `build` 即可。
`build` 会自动把新帧聚类自举进模板，人工只需要标注几帧真值。

```powershell
python D:\Tools\digitread.py watch 900        # 抓 15 分钟
# 挑几张肉眼读数值，填进 manifest.json
python D:\Tools\digitread.py build
python D:\Tools\digitread.py cv
```

优先补：含 9 的数值、含 3 的数值（尤其绿字/白字都要有）。
